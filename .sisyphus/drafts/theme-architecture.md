# Draft: Global theme architecture (dendritic Nix)

## Requirements (unconfirmed)
- Want a global “theme” system: single place defines colors + fonts.
- Easy switching; auto-applies to desktop + terminal apps.
- Apps vary: configs rendered from Nix attrsets into TOML/JSON/YAML/conf files on rebuild.
- Repo uses dendritic flake-parts modules; import=active; no Home Manager.

## Requirements (confirmed)
- Switching UX: **rebuild-only**.
- Token model (v1): **palette-first** (base16-ish palette canonical; derive semantics where needed).
- Platforms: **NixOS + Darwin**.
- Preferred architecture: **Option A** (core tokens + per-app adapters).
- v1 must-have apps: **ghostty, tmux, waybar, rofi, thunar**.

## Research Findings (repo scan)
- No existing global `jvf.*` theme/color/font option surface.
- Current theming is per-app + assets; lots of Waybar/Rofi themes in `modules/desktop/hyprland/assets/...`.
- `modules/desktop/hyprland/wallust.nix` exists: dynamic 16-color palette from wallpaper; assets reference wallust-generated colors.
- Existing terminals already have per-app font/theme settings:
  - `modules/programs/ghostty/default.nix`: `jvf.programs.ghostty.settings` default includes `theme = "Atom One Dark"` + fonts.
  - (kitty/alacritty also have their own settings; suggests adapter approach is consistent.)

## Research Findings (config delivery mechanism)
- `modules/wrappers.nix` is the main way configs land in user XDG dirs:
  - `jvf.wrappers.users.<username>.programs.<app>.configs.<filename> = <attrs|string>`.
  - Format inferred by file extension (`.toml`/`.json`/`.yaml`/`.ini`), else raw string.

## Research Findings (app-specific theming patterns)
- Ghostty: key=value config generator; currently `theme = "Atom One Dark"` + fonts; supports switching to explicit colors.
- tmux: generated `tmux.conf` as string; currently uses `pkgs.tmuxPlugins.onedark-theme`.
- Waybar/Rofi: asset-driven CSS/RASI; wallust currently provides shared color vars.

## Research Findings (deeper, adapter-specific)
### Ghostty module (modules/programs/ghostty/default.nix)
- Writes `~/.config/ghostty/config` via `jvf.wrappers.users.<username>.programs.ghostty.configs."config" = toConfigFormat cfg.settings`.
- `toConfigFormat` renders attrset → `key = value` lines; **cannot express repeated keys**.
- Current defaults hardcode:
  - `font-family = "JetBrainsMonoNL Nerd Font"`
  - `font-size = 11`
  - `theme = "Atom One Dark"` (named theme)
- Ghostty explicit palette needs multiple `palette = N=...` lines (0..15) + background/foreground/cursor.
- Adapter implication: keep `cfg.settings` as normal attrset, but append palette lines as raw string (cannot be in attrset).

### tmux module (modules/programs/tmux/*)
- tmux.conf generated by `modules/programs/tmux/_/tmux-conf.nix` and deployed to `~/.config/tmux/tmux.conf` via wrappers.
- Current theme is plugin-driven via `pkgs.tmuxPlugins.onedark-theme`; tmux.conf itself has no inline color directives.
- Adapter implication: remove onedark-theme default plugin; generate tmux style directives from `config.jvf.theme.colors` in tmux-conf generator (bg/fg, statusline, pane borders, messages, copy-mode).

### wallust system (modules/desktop/hyprland/wallust.nix + assets)
- wallust runtime scripts/template system writes multiple files under:
  - `~/.config/waybar/wallust/colors-waybar.css`
  - `~/.config/rofi/wallust/colors-rofi.rasi`
  - `~/.config/hypr/wallust/wallust-hyprland.conf`
  - plus kitty/cava targets (depending on wallust.toml)
- v1 adapters already generate waybar/rofi (and hypr) vars at rebuild time; wallust runtime would **clobber** them on wallpaper change.

## Candidate Architectures (notes)
- A) `jvf.theme.*` core options expose canonical tokens; app modules consume `config.jvf.theme.*`.
- B) Theme “packages” (data modules) selected via `jvf.theme.active = "..."`; adapters map tokens → per-app config.
- C) Base16/Base24 canonical palette + derived semantic tokens; or semantic-first + derived base16.
- D) Runtime switch script (optional) that flips active theme + triggers rebuild + targeted reloads.

## Candidate Architectures (more concrete)
### Option A (recommended): Semantic token core + per-app adapters
- One always-imported core aspect defines:
  - `options.jvf.theme.active` (string)
  - `options.jvf.theme.themes.<name>` (theme records)
  - `config.jvf.theme.current` (selected theme record)
- Each app/desktop module maps `config.jvf.theme.current.tokens` → its config format.
- Benefits: clean boundaries, minimal coupling, easy adding apps.

### Option B: Theme registry + “exports” per format
- Core theme module provides `jvf.theme.exports.{cssVars,base16,kittyConf,waybarCss,...}`
- App modules mostly include/import those exports.
- Benefits: less repeated mapping; downside: core becomes monolith; harder to keep app-specific quirks out.

### Option C: Base16-first canonical palette
- Source-of-truth is indexed palette; derive semantic roles.
- Benefits: terminal ecosystem compatibility; downside: semantics feel forced for UI components.

### Option D: Per-app theme fragments in one place
- `jvf.theme.themes.<name>.apps.kitty = { ... }`, `...apps.waybar = { ... }`
- Benefits: single file per theme; downside: duplicates app knowledge inside theme definitions; scales poorly.

## Recommended direction (tentative)
- Choose Option A; optionally add small shared helpers for conversions/derivations; keep app quirks in app modules.
